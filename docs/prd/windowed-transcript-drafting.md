# 구간 초안 기반 전체 전사본 작성 PRD

## Problem Statement

한국어 YouTube 영상의 원어 자막 초본을 만들 때 현재 파이프라인은 ASR 결과를
먼저 cue로 확정하고, 비전·기존 자막·복구 결과를 그 구조에 나중에 적용한다.
따라서 ASR의 반복 환각, 오인식, 잘못된 분절이 전체 전사본의 뼈대가 되고 다른
자료가 더 정확해도 이를 충분히 반영하기 어렵다.

실제 주행에서는 비전 결과가 대부분 사라지고, 음성이 아닌 구간에서 대량의 확인
질문이 생성됐으며, 사용자의 동의 없이 에이전트가 질문에 답했다. 내용이 무너진
전사본도 구조적으로 읽을 수 있다는 이유만으로 `finalized`와 `valid`가 됐다.
실행 중 제품 코드가 바뀌고 전체 프레임을 저장해 실행의 재현성과 자원 사용도
통제되지 않았다.

사용자는 ASR을 고치는 파이프라인이 아니라 ASR·모든 기존 자막·비전·화자 구분
자료를 함께 보고 구간별 초안을 작성한 뒤, 이를 영상 한 편의 전체 전사본으로
정리하는 파이프라인을 원한다. 자동 판단이 어려운 항목만 사용자가 확인하고,
검증 결과는 실제로 검증한 전사본에만 적용돼야 한다.

## Solution

파이프라인을 다음 흐름으로 바꾼다.

1. **전사 단계**에서 기초 전사와 참고 자료를 준비한다.
2. 영상을 5분 구간으로 나누고 최대 4개의 **구간 초안 에이전트**가 독립적으로
   초안을 작성한다.
3. **전체 전사본 작성 에이전트**가 모든 구간 초안을 종합해 영상 한 편의 전체
   전사본과 불명확한 항목을 만든다.
4. 사용자가 동의한 경우에만 불명확한 항목을 하나씩 확인한다.
5. 전사본의 구조와 알려진 품질 실패를 검증한 뒤 최종 전사본을 제공한다.

전사 단계는 원본 영상·16 kHz mono 오디오·ASR·모든 한국어 자막 트랙·실제 PTS가
연결된 2fps 프레임을 준비한다. pyannote 화자 구분은 전체 오디오에 한 번
실행하되 선택적 참고 자료로 취급한다. 실행에 실패하거나 결과가 없더라도 나머지
자료로 계속 진행한다.

각 구간 초안 에이전트는 담당 5분과 앞뒤 15초 문맥에 해당하는 모든 자료를
함께 본다. 중복 문맥도 각 에이전트가 작성하며, 판단하지 못한 항목은 주관적
confidence 대신 구체적인 이유가 있는 임시 메모로 남긴다.

전체 전사본 작성 에이전트는 구간 초안의 중복과 충돌을 직접 판단한다. 필요하면
이미 저장된 PTS 프레임을 찾아본다. 판단을 마치면 각 cue에 UUID를 한 번
부여하고, 이후 발화·화자·시각 수정에도 같은 ID를 유지한다. 동시에 말한 발화는
화자별 cue로 나누고 시간이 겹치는 것을 허용한다.

pyannote의 `SPEAKER_00` 같은 값은 실제 인물이 아니라 비슷한 목소리로 판단된
구간을 뜻한다. 구간 초안과 전체 전사본 작성 에이전트 모두 이를 인물 identity로
고정하지 않고 다른 자료와 함께 쓰는 추론 단서로만 취급한다.

## User Stories

1. 원어 자막 제작자로서 YouTube URL 하나로 전사를 시작하고 싶다. 그래야
   미디어를 직접 준비하지 않아도 된다.
2. 원어 자막 제작자로서 처리 전에 등장인물·외모·의상·등장 순서 등의 회차
   맥락을 자유롭게 입력하거나 `없음`으로 계속하고 싶다. 그래야 정해진 입력
   양식에 막히지 않는다.
3. 원어 자막 제작자로서 ASR·모든 자막·비전 자료를 함께 사용하고 싶다. 그래야
   ASR 오류나 한 자막 트랙이 전체 전사본의 기준이 되지 않는다.
4. 원어 자막 제작자로서 PTS가 연결된 2fps 프레임과 선택적 pyannote 화자 구분을
   참고 자료로 사용하고 싶다. 그래야 자원 사용을 제한하면서 장면과 화자를
   다시 판단할 수 있다.
5. 원어 자막 제작자로서 영상을 5분 구간과 앞뒤 15초 문맥으로 나눠 최대 4개까지
   병렬 처리하고 싶다. 그래야 긴 영상도 문맥을 보존하며 처리할 수 있다.
6. 원어 자막 제작자로서 구간 에이전트가 판단하지 못한 내용을 이유와 함께
   남기길 원한다. 그래야 다음 에이전트가 다시 판단할 수 있다.
7. 원어 자막 제작자로서 전체 전사본 작성 에이전트가 모든 구간 초안과 저장된
   프레임을 보고 중복과 충돌을 판단하길 원한다. 그래야 영상 한 편의 일관된
   전사본을 얻을 수 있다.
8. 원어 자막 제작자로서 수정 후에도 유지되는 cue UUID와 화자별 겹말 cue를
   원한다. 그래야 재번호 매김이나 동시 발화로 정보가 사라지지 않는다.
9. 원어 자막 제작자로서 확인 질문 전에 참여 여부를 결정하고 에이전트 제안과
   내 답변을 구분하고 싶다. 그래야 기계 판단이 사용자 승인으로 기록되지 않는다.
10. 원어 자막 제작자로서 확인을 거절해도 전체 전사본을 보존하고 싶다. 그래야
    나중에 필요하면 새 확인 절차를 시작할 수 있다.
11. 원어 자막 제작자로서 전사본 수정 시 기존 검증이 자동으로 무효화되고
    validator만 다시 `valid`를 기록하길 원한다. 그래야 옛 합격 결과가 수정된
    내용에 남지 않는다.
12. 원어 자막 제작자로서 반복 환각 같은 알려진 실패와 실행 중 코드 변경을
    차단하고 싶다. 그래야 읽을 수 있지만 사용할 수 없는 결과와 재현 불가능한
    실행을 완료로 오인하지 않는다.

## Implementation Decisions

### 처리 단계와 용어

- `기초 전사 → 구간 초안 → 전체 전사본 → 최종 전사본`을 표준 용어로 사용한다.
  각 용어의 경계는 저장소의 `CONTEXT.md`를 따른다.

### 전사 단계

- ASR 텍스트·단어 시각·모델 원본 confidence와 no-speech 신호를 가능한 범위에서
  보존한다. 에이전트가 새로 매기는 `high/medium/low` confidence는 만들지 않는다.
- 모든 수동·자동 한국어 자막 트랙을 출처 종류와 함께 보존한다. 내용이 같더라도
  제거하거나 동등한 표로 계산하지 않는다.
- 프레임은 source timeline 기준 2fps로 추출하고 실제 PTS와 frame ID를 연결한다.
  원본 전체 프레임이나 추가적인 촘촘한 프레임·clip은 생성하지 않는다.
- pyannote는 전체 오디오에 한 번 실행하고 가능한 화자 구분 결과를 보존한다.
  실패는 기록하되 전체 실행을 중단하지 않는다.

### 구간 초안 작성

- 기본 구간은 5분이고 앞뒤 15초를 함께 제공한다. 독립 구간은 최대 4개까지
  병렬 실행한다.
- 모든 구간은 중복 문맥에 해당하는 발화도 작성한다. 구간 소유권 규칙으로
  출력을 잘라내지 않는다.
- 구간 초안은 발화·시각·선택적 화자와 불명확 사항을 포함한다. 영구 cue ID나
  cue별 증거 목록은 만들지 않는다.
- 불명확 사항에는 대상 시각·필드·판단하지 못한 이유와 가능한 후보가 있으면
  후보를 기록한다.
- 각 구간에 제공한 ASR·자막·비전·pyannote 자료와 구간 초안 결과를 함께
  보존한다.

### 전체 전사본 작성

- 전체 전사본 작성 에이전트가 모든 구간 초안을 시간순으로 종합하고 중복 문맥의
  동일 발화와 충돌을 판단한다.
- 에이전트는 이미 저장된 frame manifest와 2fps 프레임을 필요할 때 직접 열람할
  수 있다. 새 프레임 추출 도구는 제공하지 않는다.
- 구간 초안의 불명확 사항은 전체 문맥과 프레임으로 다시 판단한다. 해결하지 못한
  항목만 사용자 확인 대상으로 만든다.
- pyannote 화자 구분은 인물 identity가 아니다. 같은 cluster도 잘못 묶였을 수
  있고 다른 cluster도 같은 인물일 수 있다는 제약을 모든 판단에 적용한다.
- 실제 화자는 cue별로 다른 자료와 함께 추론한다. 영상 전체에 적용하는 전역
  `cluster → person` 매핑은 만들지 않는다.
- 동시에 말한 발화는 화자별 cue로 나누며 cue 시간 중첩을 허용한다.
- 전체 전사본이 만들어진 뒤 각 cue에 불투명 UUID를 한 번 부여한다. sequence는
  표시용이며 UUID는 발화·화자·시각 수정과 재번호 매김에도 유지한다.

### 사용자 확인

- 확인 대상이 있으면 Senpi 에이전트가 먼저 확인 참여 여부를 묻는다. 동의 전에는
  개별 항목을 제시하거나 답변을 적용하지 않는다.
- `answer`는 사용자 답변이고 `suggest`는 에이전트 제안이다. 제안은 확인 항목을
  해결하거나 queue를 소진하지 않는다.
- 첫 구현은 Senpi 에이전트가 사용자 답변을 올바르게 전달한다고 신뢰한다.
- 사용자가 확인을 거절하면 해당 확인 절차를 종료하고 현재 전체 전사본을
  보존한다. 나중에 확인하려면 새 확인 절차를 시작한다.
- 잘못된 ID·중복 답변·빈 답변·손상된 기록은 전사본을 바꾸지 않는다.

### 검증과 실행 제어

- 전사본을 바꾸는 단일 저장 경로는 기존 검증 결과를 먼저 무효화하고
  `validation_status=pending`으로 바꾼 뒤 새 전사본을 원자적으로 저장한다.
- validator만 검증 상태를 쓰며 구조 검사와 내용 품질 검사의 결과와 이유를
  별도로 보존한다.
- 최소 품질 검사는 병적 반복, 비현실적인 cue 길이, 의도하지 않은 중복, 비정상
  공백과 남은 불명확 항목을 다룬다. 정상적인 동시 발화 cue 중첩은 실패로
  취급하지 않는다.
- 보호된 실제 주행에서는 제품 코드·테스트·설정·스킬 쓰기를 차단하고 run
  artifact와 로그만 쓸 수 있다.
- 실행 시작과 종료 시 source fingerprint를 비교한다. 주행 중 제품 결함을
  발견하면 같은 실행에서 수정하지 않고 중단한다.
- 기존 ASR·비전·확인·검증 구조는 가능한 한 유지한다. 새 처리 단계마다 별도
  모듈을 만드는 전면 재구성은 하지 않는다.

## Testing Decisions

- 테스트는 prompt 문구, 자연어 결과 전체, 내부 helper나 파일 배치를 고정하지
  않고 CLI와 저장된 artifact에서 관찰되는 계약을 검증한다.
- 1~2분 결정적 fixture로 기초 전사·수동 및 자동 자막·비전·pyannote·겹말·ASR
  반복 오류를 재현한다.
- ASR이 canonical cue를 직접 만들지 않고 구간 초안과 전체 전사본 작성 뒤에만
  UUID cue가 생기는지 검사한다.
- 구간 완료 순서가 달라도 최대 동시성 4와 전체 전사본 결과 계약이 유지되는지
  이벤트 기반으로 검사한다. 고정 sleep과 시간 운에 의존하지 않는다.
- pyannote가 실패하거나 결과가 없어도 나머지 자료로 구간 초안과 전체 전사본을
  만드는지 검사한다.
- 중복 문맥의 같은 발화는 하나로 정리되고 실제로 동시에 말한 발화는 겹치는
  별도 cue로 남는지 검사한다.
- 구간 초안의 불명확 메모가 전체 전사본 작성에서 해결되거나 사용자 확인
  항목으로 전환되는지 검사한다.
- 확인 동의 전 item 접근·answer 적용을 거부하고 suggestion이 item을 해결하지
  않는지 검사한다.
- 전사본 수정 과정에서 검증 무효화가 먼저 일어나며 중간 실패가 옛 `valid`를
  남기지 않는지 검사한다.
- 구조적으로 정상인 반복 환각 전사본이 내용 품질 검사에서 실패하는지 검사한다.
- 실제 YouTube 주행은 CI와 분리하고 큰 변경 뒤 명시적으로 실행해 artifact,
  source fingerprint와 검증 결과를 보존한다.

## Out of Scope

- 번역과 번역문 생성
- 최종 자막의 완전 무인 확정
- 콘텐츠 유형별 프리셋·자동 분류와 inner voice 전용 정책
- 앞 구간 결과를 다음 구간에 넘기는 연쇄 구간 처리
- 불명확 구간의 선택적 재-ASR
- 추가 프레임·contact sheet·clip 추출과 Terra·OCR 재감사
- 영상 특성에 따른 구간·문맥·fps·동시성 자동 조정
- pyannote 화자 구분의 전역 인물 매핑
- cue별 증거 ID와 에이전트 자체 confidence
- 새 처리 단계마다 모듈을 만드는 전면 아키텍처 재구성

## Further Notes

- 전체 전사본 작성은 확률적으로 중복과 충돌을 판단한다. 판단을 숨기기 위해
  결정적인 소유 규칙이나 의미 기반 dedupe 알고리즘을 추가하지 않는다.
