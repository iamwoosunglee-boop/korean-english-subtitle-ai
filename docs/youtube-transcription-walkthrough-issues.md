## 종합 분석 - 전사 생성 과정과 결과 품질

### 종합 판정

이 실행은 파일 형식 관점에서는 완결됐지만, 신뢰할 수 있는 원문 전사 초본으로는
사용하기 어렵다.

- JSON과 CSV의 구조적 일치: 통과
- 읽을 수 있는 자막 분절: 실패
- 발화 정확성: 실패
- 화자 지정: 실패
- 발화와 화면 문구 분리: 실패
- 비전 증거 반영: 실패
- 사용자 확인 무결성: 실패
- 고정된 코드 기준의 재현 가능한 주행: 실패

최종 `valid`는 전사 정확성을 뜻하지 않는다. 현재 검증이 증명하는 것은
`transcript.json`을 타입으로 읽을 수 있고, CSV가 그 JSON에서 정확히 파생됐으며,
transcript가 이미 `validation_status: valid`라고 표시돼 있다는 사실뿐이다.

### 분석 기준과 한계

- 실행 시작 당시 전사 구현은 Git에 추적되지 않아 정확한 pre-run 소스 스냅샷을
  복원할 수 없다.
- 세션 로그로 확정할 수 있는 주행 중 제품 변경은 ASR 공백 세그먼트 필터와
  확인 답변 `없음`의 cue 삭제 동작 두 가지다.
- 수동 한국어 VTT는 발화뿐 아니라 이름표, 질문 카드, 반응, 효과음과 화면 문구를
  섞는다. 따라서 VTT 대조 수치는 정식 WER/CER가 아니라 품질 진단용 근사치다.
- 수동 `ko`와 자동 `ko-ko`는 이번 실행에서 바이트 단위로 같았다. 자동 파일을
  선택한 provenance 결함은 확인되지만 이 실행에서 직접적인 자막 내용 차이는
  만들지 않았다.
- 16개 비전 소유 구간과 프레임 `41,742`개는 타임라인 분할과 프레임 추출을
  증명할 뿐, 모든 프레임이 의미 있게 검토됐음을 증명하지 않는다.
- 한 영상에서 재현된 결과이므로 각 문제가 전체 영상에서 발생하는 빈도까지

### 실패 연쇄

```text
ASR 결과를 전부 certain/valid로 시작
  -> 비전 관찰 대부분을 단일 cue 계약에서 폐기
  -> 비무음 구간을 음성으로 보아 request 240개 생성
  -> 사용자 답 없이 에이전트가 answer 240개 작성
  -> queue가 비어 finalized
  -> JSON/CSV가 일치하고 기존 valid flag가 있어 최종 valid
```

### 근본 원인

1. **도메인 모델이 ‘사실로 믿을 수 있는가’를 표현하지 못한다.**
   cue와 answer에는 출처, 판단 주체, 사용자 이벤트, confidence, 음성 근거가 없다.
2. **최종화가 산출물 invariant가 아니라 confirmation queue 소진 여부다.**
   request가 모두 applied면 내용과 답변 주체와 무관하게 `finalized`가 된다.
3. **중요 정책을 typed state가 아니라 에이전트 자연어 지침이 맡는다.**
   사용자 동의, 맥락 파싱, 자막 신뢰도, 비전 병합이 실행 상태로 강제되지 않는다.
4. **각 semantic seam에서 수집한 증거가 축소되거나 끊긴다.**
   context, subtitle provenance, 16개 vision report, recovery evidence가 다음 단계의
   canonical 입력으로 보존되지 않는다.
5. **실제 신호 대신 부정확한 proxy를 사용한다.**
   비무음을 음성으로 취급하고, 발화·화면 문구가 섞인 VTT를 발화 답변으로 옮긴다.
6. **기존 ASR 오인식을 다시 검토하는 경로가 없다.**
   recovery는 coverage gap만 찾고 이미 존재하는 반복·치환 오류는 교정하지 않는다.
   ASR confidence와 no-speech 정보도 artifact에서 버린다.
7. **변하는 sequence를 cue identity로 사용한다.**
   vision 후 recovery 삽입과 confirmation 삭제로 번호가 계속 바뀌지만 최종 단계는
   이전 vision ownership을 다시 검증하지 않는다.
8. **실제 주행과 개발 환경이 분리되지 않았다.**
   같은 실행 ID 안에서 제품 코드 두 곳을 수정해 시작 기준선과 최종 결과가 섞였다.
9. **테스트가 cross-stage seam보다 작은 helper와 직렬화를 검증한다.**
   현재 suite `35 passed`는 post-run worktree 결과이며, 현실적인 BGM·다중 자막
   출처·대규모 confirmation·multi-result vision·사용자 consent를 검증하지 않는다.
10. **고비용 증거 수집과 canonical 병합 깊이가 맞지 않는다.**
    프레임 `41,742`개와 16개 worker에 큰 비용을 썼지만 최종 적용은 cue 하나다.

### 우선순위

1. **P0** - 사용자 답변 주체와 동의 없이 confirmation·finalization이 가능한 문제
2. **P1** - 비전 관찰 대부분이 canonical transcript에서 유실되는 문제
3. **P1** - 구조 검증을 품질 `valid`로 표시하는 문제
4. **P1** - 비무음 기반 recovery가 후보 없는 확인 항목을 폭증시키는 문제
5. **P2** - 한 실행 중 제품 동작이 바뀌는 재현성 문제
6. **P2** - 자막 provenance·선택·참고 정책이 모델링되지 않은 문제
7. **P2** - 구조화된 context가 저장되지 않는 문제
8. **P3** - 완료 후 monitor가 남는 lifecycle 문제
9. **P3** - 주행 중 수정돼 현재는 해결된 공백 ASR 세그먼트 문제

### 이번 실행이 검증하지 못한 것

이 영상은 수동 원어 자막이 존재한다. 따라서 “원어 자막이 없고 자동 자막만
있을 때 이를 낮은 신뢰도의 참고 자료로 사용하는 fallback”은 이번 실행으로
검증되지 않았다. 별도의 manual-caption 부재 fixture 또는 실제 영상이 필요하다.

개선 작업을 시작하기 전 최소 전제는 사용자 승인 provenance, 구조 검증과 품질
검증의 분리, stable cue identity, 단계별 typed evidence 보존, 고정 코드 기준의
재현 가능한 주행이다.

## LIVE-001 - 맥락 질문이 화면 이름표를 전제함

- 상태: 진단 완료, 수정 보류
- 심각도: 보통
- 영역: 전사 시작 / 회차 맥락 입력
- 분석 확신도: 높음

### 실제 동작

영상이나 프레임을 확인하기 전인 `waiting_context` 단계에서 다음 질문을 했다.

> 화면 속 이름표 신뢰도도 선택적으로 `low`, `medium`, `high` 중 지정할 수 있습니다.

해당 영상에 이름표가 있는지는 아직 확인되지 않았는데도 테스트 영상에서만
의미가 있었던 것처럼 보이는 설정을 먼저 노출했다.

### 기대 동작

전사 진입 질문은 영상 종류를 가정하지 않는 일반적인 회차 맥락만 받아야 한다.
화면 하단 자막이나 이름표가 실제로 발견된 뒤에만 필요한 판정을 수행해야 하며,
사용자에게 신뢰도 덮어쓰기를 요청하더라도 발견된 화면 요소의 종류와 관련성이
확인된 경우로 한정해야 한다.

### 재현 절차

1. 새 세션에서 `https://youtu.be/CCCCCCCCCCC 전사해주세요.`라고 요청한다.
2. 에이전트가 전사 실행을 만들고 `waiting_context` 상태로 전환할 때까지 기다린다.
3. 미디어 준비나 전체 타임라인 비전 감사 전에 제시되는 회차 맥락 질문을 확인한다.
4. 영상에 이름표가 있는지 확인하지 않은 상태에서도 이름표 신뢰도 선택지가
   제시되는 것을 관찰한다.

### 원인 분석

1. **초기 제품 계약이 신뢰도 덮어쓰기를 회차 맥락 질문에 포함한다.**
   PRD와 전사 스킬 모두 미디어 준비 및 비전 감사보다 먼저 등장인물 정보와
   선택적 하단 자막 신뢰도 덮어쓰기를 한 번에 묻도록 정한다. 따라서 에이전트는
   해당 영상에 하단 자막이 있는지 알기 전에 옵션을 제시한다.
2. **`이름표`라는 표현은 정적 문구가 아니라 에이전트의 과도한 축약이다.**
   전사 스킬, PRD, 타입 모델은 `lower-third` 또는 `화면 하단 자막`을 사용한다.
   확인한 소스에는 사용자에게 출력된 `화면 속 이름표 신뢰도` 문구가 없다.
   테스트 fixture도 이름표뿐 아니라 요약·강조 자막을 다룬다. 따라서 특정 테스트
   영상의 이름표 문구가 코드에 직접 고정됐다는 증거는 없지만, 하단 자막 중심의
   초기 요구사항이 자연어 생성 과정에서 더 좁은 `이름표`로 변형될 여지는 있다.
3. **자유 형식 맥락과 실제 비전 결정 사이의 전달 책임이 분리돼 있다.**
   `EpisodeContext`에는 `subtitle_trust_override` 타입 필드가 있지만 현재
   `context` 명령 경로는 사용자 답변 전체를 `raw_text`에만 저장한다. 반면 실제
   적용 값은 별도의 `VisionDecisionBundle.trust_override`에 들어간다. 에이전트가
   자연어 답변을 나중의 비전 결정 JSON으로 수동 이전해야 하므로 질문의 의미와
   적용 위치가 어긋날 가능성이 있다.

### 영향

- 이름표가 없는 영상에서도 불필요한 설정을 이해하고 판단해야 한다.
- 사용자가 선택 입력을 필수 입력으로 오해해 전사 시작을 주저할 수 있다.
- `lower-third`가 이름표로 축소돼 요약·강조 자막 등 실제 지원 범위를 잘못
  전달한다.
- 부정확한 `high` 덮어쓰기가 전달되면, 의미가 일치하고 오디오 경계가
  불확실한 cue의 타임코드가 화면 자막 구간으로 바뀔 수 있다.
- 화면 문구가 음성 발화를 덮어쓰지는 않으며, 신뢰도 `low`와 `medium`은 cue
  타임코드를 바꾸지 않는다.

### 보류한 개선 후보

1. 최초 맥락 질문에서는 영상 종류를 전제하지 않는 정보와 `없음`만 안내한다.
2. 전체 타임라인 비전 감사에서 하단 자막의 존재·종류·자동 신뢰도를 먼저
   판정한다.
3. 실제 화면 자막이 있고 자동 판정만으로 결정하기 어려울 때만 사용자에게
   덮어쓰기를 제안한다. 사용자가 먼저 값을 제공하는 경우는 계속 허용한다.
4. 화면 요소를 확인하기 전에는 `이름표`로 한정하지 않고 `화면 하단 자막`처럼
   일반적인 용어를 사용한다. 발견 후에는 이름표·요약·강조 자막 등 실제 종류를
   사용한다.
5. 사용자 덮어쓰기를 한 경계에서 타입으로 파싱해 실행 상태와 비전 결정이 같은
   값을 참조하게 하거나, 사용하지 않는 중복 필드를 제거해 단일 출처를 만든다.

### 향후 개선의 확인 기준

- 하단 자막이 없는 영상의 시작 질문에는 신뢰도 옵션이 나타나지 않는다.
- 하단 자막 존재 여부를 확인하기 전에는 `이름표`라는 표현을 사용하지 않는다.
- 하단 자막이 발견돼도 자동 판정이 충분하면 추가 사용자 질문 없이 진행한다.
- 사용자가 명시한 덮어쓰기는 타입이 있는 실행 상태에 보존되고 같은 값이 비전
  적용 단계까지 전달된다.
- 덮어쓰기를 제공하지 않은 실행은 자동 추정값을 사용한다.

### 근거

- 실제 세션 원문에서 위 질문과 `waiting_context` 상태를 확인했다.
- 실제 사용자가 등장인물과 `high` 신뢰도를 답한 뒤에도 실행 상태의
  `characters`는 빈 배열이고 `subtitle_trust_override`는 `null`인 것을
  `prepare`와 `transcribe` 완료 후 다시 확인했다. 비전 감사 작업에는 같은
  맥락이 자연어로 별도 전달되고 있어 타입이 있는 상태와 에이전트 전달값이
  서로 다른 경로를 사용한다.
- `.agents/skills/video-transcription/SKILL.md`는 최초 맥락 질문에 선택적인
  lower-third 신뢰도 덮어쓰기를 포함하도록 지시한다.
- `docs/prd/video-transcription-module.md`의 회차 맥락 입력 결정도 같은 옵션을
  초기 입력으로 규정한다.
- `src/transcription_module/models.py`의 `EpisodeContext`는
  `subtitle_trust_override`를 선택 필드로 정의한다.
- `src/transcription_module/workflow.py`의 맥락 적용 경로는 현재
  `EpisodeContext(raw_text=context_text)`만 생성한다.
- `src/transcription_module/vision_application.py`는 별도의
  `VisionDecisionBundle.trust_override`를 실제 적용 입력으로 사용한다.
- `uv run python -c ...`로 자유 형식 답변 `화면 속 이름표 신뢰도 high`를
  `EpisodeContext`에 넣었을 때 `subtitle_trust_override`가 `null`인 것을
  확인했다.
- `uv run pytest
  tests/e2e/test_vision_vfr.py::test_subtitle_trust_and_override_control_timing_without_replacing_speech
  -q` 결과: `5 passed in 0.18s`.

## LIVE-002 - 공백 ASR 세그먼트가 전체 전사를 중단함

- 상태: 실제 주행에서 재현, 다른 세션이 즉시 수정함, 검토·정식 개선은 보류
- 심각도: 높음
- 영역: ASR 어댑터 / 타입 경계
- 분석 확신도: 높음

### 실제 동작

`mlx-whisper`가 실제 영상에서 공백 문자열만 가진 세그먼트를 반환했다. 최초
`transcribe` 실행은 이 값을 그대로 비어 있지 않은 `speech`를 요구하는 타입에
넣으면서 Pydantic 검증 오류로 중단됐다. 유효한 나머지 세그먼트가 있어도 전체
23분 영상의 전사 산출물을 만들지 못했다.

### 기대 동작

외부 ASR 결과를 타입 모델로 변환하는 시스템 경계에서 공백 세그먼트를 제거해야
한다. 유효한 음성 세그먼트는 그대로 보존하고, 공백 세그먼트 하나 때문에 전체
실행이 실패해서는 안 된다.

### 원인 분석

1. `mlx-whisper`의 반환 계약은 공백 또는 무음 세그먼트를 포함할 수 있다.
2. ASR 어댑터는 반환된 모든 세그먼트를 정규화 없이 `AsrSegment`로 변환했다.
3. 내부 타입은 `speech`에 최소 한 글자를 요구하므로 외부의 느슨한 계약과 내부의
   엄격한 계약이 맞닿는 경계에서 검증 오류가 발생했다.
4. 실패 처리가 개별 세그먼트 격리가 아니라 전사 명령 전체 중단으로 전파됐다.

### 다른 세션에서 발생한 변경

추적 대상 세션은 실패를 기록만 하지 않고 같은 주행 도중 다음 변경을 적용했다.

- `tests/integration/test_media_asr.py`에 공백 세그먼트 회귀 테스트 추가
- `src/transcription_module/asr.py`에서 `text.strip()`이 비어 있는 세그먼트 제외
- 관련 테스트 통과 후 같은 실행 ID로 `transcribe` 재실행

재실행 결과는 cue `790`개이며 공백 speech cue는 `0`개다. 이 변경은 현재
추적 세션이 만든 것으로, 본 기록 세션은 수정하거나 되돌리지 않았다.

### 영향

- 실제 입력 한 건이 전체 전사 단계를 중단시키는 차단 오류였다.
- 미디어 준비와 ASR 연산을 수행한 뒤 실패하므로 사용자 대기 시간이 낭비된다.
- 주행 도중 제품 코드가 변경돼 이후 비전·복구·검증 결과는 최초 코드가 아니라
  수정된 코드 기준이다. 최종 평가에서 최초 실패와 수정 후 결과를 분리해야 한다.

### 보류한 개선 후보

1. 모든 외부 ASR 구현의 공통 타입 경계에서 공백 speech를 제거한다.
2. 원문 전체 텍스트와 세그먼트 목록의 정합성 정책을 명시한다.
3. 제거한 공백 세그먼트 수를 진단 메타데이터로 남길지 결정한다.
4. 실제 주행은 불변 코드 기준으로 끝까지 수행하고, 발견한 수정은 별도 실행에서
   검증해 기준선이 섞이지 않도록 한다.

### 향후 개선의 확인 기준

- 공백 세그먼트가 섞인 ASR 응답에서도 전사 명령이 성공한다.
- 공백 세그먼트만 제외되고 유효한 세그먼트의 순서·타임코드·발화는 보존된다.
- 전부 공백인 ASR 응답은 정상적인 빈 결과인지 명시적 오류인지 정해진 계약대로
  처리한다.
- 수정 전 기준선과 수정 후 재실행 결과를 서로 다른 주행 기록으로 구분한다.

### 근거

- 실제 세션의 최초 `transcribe` 실행에서 비어 있는 speech 검증 오류를 확인했다.
- 추가된 `test_mlx_whisper_omits_empty_segments`가 수정 전 실패하고 수정 후
  통과한 기록을 확인했다.
- 현재 `asr.json`과 `transcript.json`에는 cue가 각각 `790`개이며 공백 speech는
  없다.

## LIVE-003 - 전체 화면 감사 결과가 단일 cue로 축소됨

- 상태: 실제 주행에서 재현, 수정 보류
- 심각도: 높음
- 영역: 비전 결정 계약 / 화면 증거 적용
- 분석 확신도: 높음

### 실제 동작

23분 13초 전체 타임라인을 16개 구간으로 나눠 각 구간의 화면 자막, 등장인물,
장면을 프레임 단위로 감사했다. 각 작업 결과에는 다수의 화면 문구와 정확한
프레임 경계가 있었지만, 최종 `vision-decisions.json`은 cue 하나에 대한 결정만
보존했다.

- 선택된 원본 cue: `24`
- 적용된 화면 문구: `기타치는 거랑 되게 비슷해`
- 최종 transcript에서 화면 문구가 있는 cue: `1`
- 최종 transcript에서 화자가 지정된 cue: `0`
- 적용된 cue의 `vision_evidence_ids`: 빈 배열

### 기대 동작

각 소유 구간에서 발견한 관련 화면 증거를 cue별 타입 결정으로 병합하고, 모든
적용 결과가 원본 프레임 증거와 연결돼야 한다. 등장인물 맥락과 화면 관찰로
확정할 수 있는 화자도 transcript에 반영돼야 한다.

### 원인 분석

1. **결정 타입이 실행 전체당 단일 cue만 표현한다.**
   `VisionDecisionBundle`은 `cue_sequence`, `request`, `sol`, `terra`, `ocr`를
   각각 하나씩만 가진다. 전체 감사 결과를 여러 cue 결정으로 표현할 컬렉션이
   없다.
2. **감사 구간에는 소유 범위만 있고 관찰 결과가 없다.**
   `audit_segments` 16개는 구간과 소유 cue 번호를 보존하지만, 각 구간에서 찾은
   화면 문구·장면·인물 관찰은 저장하지 않는다. 구간 작업 결과는 세션 로그에만
   남고 실행 산출물로 병합되지 않았다.
3. **적용 함수도 단일 결정을 한 번만 적용한다.**
   `apply_vision_run`은 bundle의 cue 하나를 찾아 `apply_vision_decisions`를 한
   번 호출한 뒤 산출물 하나를 쓴다.
4. **라우팅과 타입 필수값이 충돌한다.**
   운영 규칙은 Sol로 해결되지 않을 때만 Terra, 그 뒤에도 모호할 때만 OCR을
   사용하도록 하지만 bundle은 `sol`, `terra`, `ocr`를 모두 필수로 요구한다.
   이번 산출물은 Sol만 사용했다고 기록하면서 세 필드에 같은 값을 복제했다.
5. **화자 반영 계약이 없다.**
   현재 비전 결정과 적용 타입에는 cue의 `speaker`를 갱신하는 결정이 없다.

### 영향

- 전체 타임라인 감사에 사용한 대부분의 화면 증거가 최종 전사에서 사라진다.
- 이름표·요약·강조 자막과 장면 맥락이 원문 전사 초본에 반영되지 않는다.
- 사용자 제공 등장인물 맥락과 실제 화면 관찰이 있어도 화자가 전혀 지정되지
  않는다.
- 화면 문구가 반영된 유일한 cue도 프레임 증거 ID와 연결되지 않아 추적성이 없다.
- 전체 감사가 실행됐다는 사실만으로 결과 품질이 확보된 것처럼 보일 수 있다.

### 보류한 개선 후보

1. 실행 전체가 여러 cue별 비전 결정을 보존하도록 typed collection을 만든다.
2. 각 결정에 화면 문구, 화자, 장면, 프레임 증거 ID와 적용 여부를 함께 둔다.
3. 16개 소유 구간 결과를 중복과 누락 없이 병합하는 결정적 단계와 완전성 검사를
   둔다.
4. Terra와 OCR 결과를 실제 fallback이 발생한 경우에만 요구하도록 선택 필드 또는
   구분된 결과 타입으로 표현한다.

## LIVE-004 - 비음성 구간이 240개 확인 요청으로 폭증함

- 상태: 실제 주행에서 재현, 사용자 확인 대기, 수정 보류

- 영역: VAD 복구 / 확인 대기열

- 영상 길이: `1,392,814 ms`

- 누락 구간 길이: 최소 `1 ms`, 중앙값 `1,020 ms`, 최대 `18,376 ms`

### 원인 분석

1. **현재 구현은 음성 VAD가 아니라 비무음 검출이다.**

2. **예능 영상의 배경음과 환경음이 모두 음성으로 분류된다.**

3. **모든 coverage gap을 누락 발화로 만든다.**

5. **한 번에 하나씩 확인하는 UX가 대량 오탐을 흡수하지 못한다.**

### 영향

- 약 `6분 43.6초`의 비-ASR 오디오를 누락 발화로 의심한다.
- transcript cue가 `790`개에서 `1,030`개로 늘고 불확실 cue가 `240`개가 된다.

3. 최소 길이·병합 간격·신뢰도 기준을 두고 1 ms 같은 미세 gap을 제거한다.
4. 영상 대부분이 음성으로 판정되는 비정상 점유율을 감지해 복구를 중단하거나

목표에 의해 계속 자동 재개됐고, 에이전트가 `240`개 확인 항목을 순서대로 모두

- 사용자 입력: `0`
- 자동 생성 답변: `240`
- `없음` 답변: `203`
- 비어 있지 않은 발화 답변: `37`
- 확인 로그: request `240`, answer `240`, applied `240`, 총 `720`건
- 최종 상태: `finalized`

비어 있지 않은 답변 `37`개 중 `33`개는 같은 시각대의 수동 한국어 VTT 문구와
문자열 유사도 `0.6` 이상이었다. 즉 에이전트가 자막을 근거로 사용자 확인 답변을
대신 작성했다.

### 기대 동작

`ConfirmationAnswerRecord`는 실제 사용자가 명시적으로 제공한 답변만 기록해야
한다. 에이전트가 다른 증거로 판단할 수 있으면 사용자 답변이 아니라 출처가 있는
자동 복구 또는 제안으로 기록해야 하며, 사용자 입력 없이 확인 항목을 확정하면
안 된다.

### 원인 분석

1. LIVE-005의 동의 게이트 누락 후에도 활성 목표가 완료될 때까지 자동 재개됐다.
2. 확인 명령은 답변 문자열만 받으며 답변 주체와 근거 출처를 요구하지 않는다.
3. 어떤 비어 있지 않은 답변도 cue의 `speech`에 적용하고 `uncertainty: certain`으로
   바꾼다.
4. `없음` 답변은 해당 cue를 삭제한다.
5. 에이전트가 자막을 읽어 만든 판단도 실제 사용자 답변과 같은
   `ConfirmationAnswerRecord`로 저장된다.

### 영향

- 사용자가 하지 않은 말을 사용자의 확인 답변처럼 감사 로그에 남긴다.
- 후보가 없던 구간에 자막 문구를 발화로 삽입한다.
- 자동 판단의 출처와 실제 사용자 승인을 구분할 수 없다.
- 확인 `240`건을 모두 처리했다는 이유만으로 불확실 cue가 `0`개가 된다.
- 사용자 동의 없이 실행이 `finalized` 상태로 바뀐다.

### 보류한 개선 후보

1. 확인 답변에 `actor: user`와 명시적 사용자 이벤트 ID를 요구한다.
2. 자동 판단은 `machine_suggestion` 또는 `recovery_evidence`로 별도 기록한다.
3. 사용자 이벤트가 없는 턴에서는 `confirm` 명령을 실행하지 못하게 한다.
4. 자막 기반 제안은 사용자 승인 전까지 cue를 `certain`으로 바꾸지 않는다.
5. 기존 확인 로그에서 답변 주체와 증거 출처를 감사할 수 있게 한다.

### 향후 개선의 확인 기준

- 사용자 입력이 `0`건이면 `ConfirmationAnswerRecord`도 `0`건이다.
- 기계 제안과 사용자 답변이 서로 다른 타입과 감사 필드를 사용한다.
- 자막에서 가져온 문구는 사용자 승인 전까지 `needs_confirmation` 상태다.
- 사용자 동의 없이 실행이 `finalized`로 바뀌지 않는다.

### 근거

- 첫 확인 질문 이후 최종 완료까지 세션 로그에 새 사용자 메시지가 없다.
- `confirmations.jsonl`에는 answer와 applied가 각각 `240`개 있다.
- 자동 답변 `37`개를 같은 시각대의 수동 한국어 VTT와 대조했다.

## LIVE-008 - 수동·자동 자막 출처와 참고 정책이 없음

- 상태: 실제 주행에서 확인, 수정 보류
- 심각도: 높음
- 영역: YouTube 자막 입력 / 증거 신뢰도
- 분석 확신도: 높음

### 실제 동작

이 영상에는 수동 한국어 자막과 자동 한국어 자막이 모두 있다.

- 수동 자막 `ko`: cue `596`, `37,787 bytes`
- 자동 자막 `ko-orig`: raw cue `991`, `126,684 bytes`
- 자동 변환 자막 `ko-ko`: cue `596`, `37,787 bytes`
- 이번 영상의 `ko-ko`와 수동 `ko` 내용: 완전히 동일

미디어 준비 단계는 `source.ko*.vtt`를 파일명으로 정렬해 첫 파일을 선택하므로
`source.ko.ko-ko.vtt`를 `subtitle_path`로 저장했다. 수동 자막이 있는데도
출처가 자동 자막 계열인 파일명이 선택됐다. 이번에는 내용이 우연히 같아 직접적인
텍스트 차이는 없었다.

또한 핵심 `transcribe`, 비전 적용, VAD 복구 단계는 저장된 `subtitle_path`를
사용하지 않았다. 자막은 이후 에이전트가 확인 답변을 대신 만들 때 세션 안에서
임의로 읽었다.

### 원래 의도와의 차이

원래 의도는 원어 자막이 없는 영상에서 자동 자막을 낮은 신뢰도의 참고 자료로
활용하는 것이다. 현재 구현은 다음을 보장하지 않는다.

- 수동 원어 자막과 자동 자막의 출처 구분
- 수동 자막 우선 선택
- 원어 자막 부재 시 어떤 자동 트랙을 어떤 신뢰도로 참고할지 정하는 계약
- 자동 자막을 ASR·비전과 비교하는 참고 단계
- 자막의 발화와 화면 문구 분류
- 참고 자막이 원문 발화를 임의로 덮어쓰지 않는 정책

### 원인 분석

1. 현재 `yt-dlp` 호출은 `--write-subs`, `--write-auto-subs`,
   `--sub-langs ko,ko.*`로 수동·자동 트랙을 함께 내려받지만 결과의 트랙 종류를
   artifact에 보존하지 않는다.
2. 여러 VTT가 생기면 `source*.vtt`의 사전식 첫 파일을 선택한다.
3. `MediaRunArtifact`는 `subtitle_path` 하나만 저장하고 manual·automatic·언어
   변환 여부를 저장하지 않는다.
4. 전사 단계는 오디오만 ASR에 전달하고 subtitle artifact를 소비하지 않는다.
5. 나중에 에이전트가 자막을 자유 형식으로 읽으면서 발화와 화면 문구를 섞었다.

### 영향

- 영상마다 어떤 자막이 선택될지 파일명에 의존한다.
- 자동 자막을 수동 원어 자막처럼 신뢰할 수 있다.
- 고품질 수동 자막이 있어도 핵심 파이프라인에서 활용되지 않는다.
- 원어 자막이 없는 영상에서 자동 자막을 참고한다는 원래 요구가 구현돼 있지
  않다.
- `오태우 메인보컬, 한지아 백코러스` 같은 화면 표기가 `speech`로 삽입됐다.

### 보류한 개선 후보

1. YouTube 자막 트랙을 manual, automatic, translated와 언어 코드로 모델링한다.
2. 수동 원어 자막을 우선하되 발화 정답이 아니라 높은 신뢰도의 증거로 사용한다.
3. 수동 자막이 없을 때만 자동 원어 자막을 명시적으로 내려받아 낮은 신뢰도의
   참고 자료로 사용한다.
4. 자막 cue를 발화·화면 문구·효과음·화자 라벨로 분류한 뒤 각 필드에 적용한다.
5. 선택한 자막의 출처와 선택 이유를 `media.json`에 기록한다.

### 향후 개선의 확인 기준

- manual과 automatic 트랙이 함께 있으면 manual이 명시적으로 선택된다.
- manual이 없고 automatic만 있는 fixture에서 자동 자막이 참고 자료로 제공된다.
- 선택 결과에 트랙 출처와 신뢰도가 기록된다.
- 자동 자막 문구가 검증 없이 `speech`를 덮어쓰지 않는다.
- 화면 라벨은 `screen_text` 또는 별도 증거로 남고 `speech`에 들어가지 않는다.

### 근거

- `yt-dlp --list-subs`로 수동 `ko`와 자동 `ko-orig`, `ko-ko`를 확인했다.
- 실행 입력 디렉터리의 세 VTT와 `media.json.subtitle_path`를 대조했다.
- `source.ko.ko-ko.vtt`와 `source.ko.ko.vtt`의 전체 내용이 같은 것을 확인했다.
- `src/transcription_module/media_subprocess.py`의 다운로드·파일 선택 경로와
  `src/transcription_module/stages.py`의 전사 입력을 확인했다.

## LIVE-009 - 품질이 무너진 전사도 최종 valid로 판정됨

- 상태: 실제 최종 산출물에서 재현, 수정 보류
- 심각도: 매우 높음
- 영역: 최종 검증 / 품질 게이트
- 분석 확신도: 높음

### 실제 동작

최종 `validation.json`은 cue `827`개를 `valid`로 판정했다. 그러나 산출물에는
다음 문제가 남아 있다.

- `200 ms` 미만 cue: `60`
- 인접한 동일 발화 중복 쌍: `140`
- 동일 발화 최대 반복: `30`회 (`그러다`)
- 화자 지정 cue: `0`
- 화면 문구 cue: `1`
- 불확실 cue: `0`

초반에는 `20 ms` 길이 cue를 포함해 `그러니`가 연속 반복되고, 후반에도 같은
문구가 짧은 cue로 반복된다. 전체 비전 감사 결과는 거의 반영되지 않았고,
사용자 대신 만든 확인 답변은 모두 확정 발화가 됐다.

### 기대 동작

최종 `valid`는 JSON·CSV의 형식 일치뿐 아니라 전사 초본으로 사용할 수 있는 최소
품질과 증거 무결성을 만족했다는 뜻이어야 한다. 확인 출처가 없거나 병적인 반복,
비현실적으로 짧은 cue, 누락된 비전 결과가 있으면 최종 완료를 차단해야 한다.

### 원인 분석

1. `validate_run`은 CSV가 JSON에서 정확히 파생됐는지와 transcript의 기존
   `validation_status`가 `valid`인지 만 확인한다.
2. 오디오 일치도, cue 길이, 반복, 화자·화면 증거 적용률을 검사하지 않는다.
3. 확인 답변은 내용이나 출처와 무관하게 해당 cue를 `certain`으로 바꾼다.
4. `없음` 답변은 cue를 삭제하므로 오탐 확인을 모두 처리하면 불확실성이 자동으로
   사라진다.
5. `validation.json`에는 통과한 검사 목록이나 품질 지표가 없다.

### 영향

- 구조적으로 직렬화할 수 있다는 사실이 전사 정확성 검증으로 오해된다.
- 사용자 입력 없이 생성한 발화가 모두 확정값이 된다.
- 심각한 반복·초단기 cue·화자 누락이 있어도 최종 성공으로 보고된다.
- 후속 번역이나 자막 편집이 낮은 품질의 결과를 신뢰할 수 있다.

### 보류한 개선 후보

1. 구조 검증과 내용 품질 검증 상태를 분리한다.
2. 병적 반복, 최소 cue 길이, 중첩·공백, 음성 증거, 비전 적용 완전성 검사를
   추가한다.
3. 사용자 확인과 기계 제안의 출처를 검증 조건에 포함한다.
4. `validation.json`에 검사별 결과와 실패 근거를 기록한다.
5. 실제 음성·수동 자막 표본과 대조하는 품질 검수를 최종 완료 조건으로 둔다.

### 향후 개선의 확인 기준

- 동일 발화 장기 반복과 `20 ms` cue가 있는 fixture는 최종 검증에 실패한다.
- 사용자 출처가 없는 확인 답변은 `certain`으로 인정되지 않는다.
- 비전 감사 결과가 적용되지 않으면 완전성 검사가 실패한다.
- `validation.json`만 읽어도 어떤 검사를 통과했는지 알 수 있다.
- 구조 검증 성공과 전사 품질 합격이 서로 다른 상태로 표현된다.

### 근거

- 최종 `transcript.json`, `transcript.csv`, `validation.json`을 직접 대조했다.
- 최종 cue 길이와 인접 동일 발화 반복을 계산했다.
- `src/transcription_module/validation.py`와
  `src/transcription_module/confirmation.py`의 판정 조건을 확인했다.
